# 2. The whole RAG pipeline in one mental model

## Definition

**Retrieval-Augmented Generation (RAG)** is an architecture in which an application retrieves relevant external information and provides that information to a language model as context when generating an answer.

## Why it exists

A language model's parameters are not a live, queryable copy of your private documents. It may not know recently updated policies, internal company information, proprietary manuals, or the exact source text you need it to use. RAG lets an application look up that information at query time.

## Two separate flows

### A. Indexing/ingestion flow — usually done before users ask questions

```text
Source files / database / website
        ↓
Load and parse
        ↓
Normalize and clean
        ↓
Split into chunks
        ↓
Attach source metadata and stable IDs
        ↓
Embed each chunk
        ↓
Write text + vector + metadata to a vector index/store
```

### B. Query-time flow — done for each question

```text
User question
    ↓
Optional query rewriting
    ↓
Embed question using the same embedding space
    ↓
Vector search (and optionally keyword/metadata filters)
    ↓
Retrieve top-k candidate chunks
    ↓
Build prompt: instructions + question + retrieved context
    ↓
Call the LLM
    ↓
Return answer, ideally with source references
```

### The key design principle

**Do not re-embed the full corpus for every question.** Generate and store document embeddings during ingestion. At query time, embed the question, search the index, and send only the selected context onward. The OpenAI/Gemini semantic-search exercises teach the same idea.

## What RAG does not guarantee

RAG can make answers more grounded in retrieved material, but it does not guarantee truth. Retrieval can miss the correct chunk, return irrelevant text, expose unauthorized data, or supply malicious instructions embedded in a document. The model can still misunderstand context or make unsupported claims. Evaluate retrieval and generation separately.

## Typical use cases

- Internal HR/policy assistant.
- Support assistant grounded in product manuals.
- Q&A over research papers or course notes.
- Document comparison and question answering.
- Search over code/documentation.
- Search systems that need both source text and generated summaries.

# 3. Prompting vs RAG vs fine-tuning

| Approach | Definition | Use when | Main limitation |
|---|---|---|---|
| Prompt engineering | Carefully designs instructions, examples, and context supplied to a model. | You need to specify behavior, output format, role, or task without changing model weights. | It cannot provide large private corpora unless you put the relevant content in the context. |
| RAG | Retrieves relevant external data and inserts it into the prompt at run time. | Facts change, source grounding matters, or users need answers over private/domain documents. | Retrieval quality and context construction become critical system components. |
| Fine-tuning | Updates model parameters using task examples or training data. | You need to adapt style, format, domain behavior, or task patterns that are hard to convey through prompts alone. | It is not a live database update; factual changes may require retraining, and it does not automatically provide citations. |

**Interview answer:** “I use prompting to control how the model responds, RAG to supply the right external facts at inference time, and fine-tuning to change the model’s learned behavior. They solve different problems and can be combined.”

# 4. Ingestion, parsing, documents, and metadata

## 4.1 Definitions

- **Ingestion:** Bringing data from its source into the retrieval pipeline.
- **Parsing:** Turning a file or source format into usable text and structured content.
- **Preprocessing:** Cleaning, normalizing, filtering, or transforming parsed content before indexing.
- **Document:** In LangChain, commonly a `Document` object containing `page_content` and `metadata`.
- **Chunk:** A smaller, retrievable segment derived from a source document.
- **Metadata:** Structured attributes about a chunk, such as source path, page number, URL, document title, access level, timestamp, or topic.
- **Provenance:** Information that lets you trace a retrieved chunk back to the original source.

## 4.2 Why metadata matters

Text tells the model what a chunk says. Metadata helps the application decide which chunks are eligible and helps it cite the answer. Useful metadata can include:

```python
metadata = {
    "source": "employee_handbook.pdf",
    "page": 12,
    "department": "HR",
    "document_version": "2026-03",
    "access_group": "employees",
}
```

Use stable identifiers. If document IDs change randomly on every run, incremental updates and deletions become hard. Avoid putting secrets or unnecessary personal data in metadata.

## 4.3 Common loaders and their purpose

| Data source | Common approach | Important consideration |
|---|---|---|
| TXT/Markdown | `TextLoader` or a Markdown loader | Encoding, headings, tables, and code blocks may matter. |
| Directory of text files | `DirectoryLoader` + `TextLoader` | Check glob patterns, hidden files, encoding, and error handling. |
| PDF | `PyPDFLoader` | Text extraction may scramble multi-column layouts, headers, tables, or scanned pages. OCR may be needed. |
| Word/DOCX | `Docx2txtLoader` or another DOCX parser | Tables, headers, footnotes, and layout might not be preserved exactly. |
| CSV | `CSVLoader` or pandas | Decide whether each row is a document; preserve column names and row IDs. |
| Excel | pandas `read_excel` or an Excel-specific loader | Sheets, merged cells, formulas, and cell types need deliberate treatment. |
| JSON | Python `json` or `JSONLoader` | Select meaningful fields with a schema/path; do not blindly embed the entire serialized object. |
| SQL database | Parameterized queries and row-to-document conversion | Respect access controls; select only needed columns and keep primary-key provenance. |
| Web pages | Web/document loader | Remove navigation boilerplate and keep URL/title/timestamp metadata. |

The syllabus specifically covers text loaders, PDF issues, Word, CSV/Excel, JSON, and SQL parsing. The uploaded notebooks mostly demonstrate text-file loading plus manual text Documents; they do not prove that every loader type above has already been implemented.

```python
for row_number, row in frame.iterrows():
    values = row.where(pd.notna(row), "").to_dict()

    excel_docs.append(Document(
        page_content=content,

    ))
```

```python
json_docs = [
    Document(
```

SQL result rows should be transformed in the same deliberate way: one row or a meaningful group becomes a `Document`, text contains the fields users need to search, and metadata retains the primary key/source. Use parameterized SQL, not string concatenation with untrusted input.

## 4.5 PDF and parsing failure modes

- A PDF may contain scanned images rather than a text layer; ordinary text extraction will return little or no content.
- Multi-column layouts can be read in the wrong order.
- Tables can lose row/column relationships.
- Repeated headers/footers can pollute every chunk.
- Page references must be preserved if answers need citations.
- OCR introduces its own errors and should be validated on important documents.

**Rule:** Inspect actual parsed output before embedding it. A good embedding model cannot recover content that the parser failed to extract.

# 5. Text splitting and chunking

## Definition

**Chunking** divides long content into smaller units that can be embedded, indexed, retrieved, and placed into a model context more precisely.

## Why not embed an entire large document?

A document may cover many topics. One vector for the whole document can blur several subjects into one representation, while a very long document may also exceed model limits. Smaller chunks let retrieval select a focused passage.

## Main terms

- **Chunk size:** Target maximum size of each chunk. In the notebook examples, `length_function=len` means the count is characters, not tokens.
- **Chunk overlap:** Number of characters/tokens repeated across neighbouring chunks to reduce boundary information loss.
- **Separator hierarchy:** Preferred split points such as paragraph breaks, newlines, spaces, and then smaller units.
- **Semantic chunking:** Splitting based on meaning similarity between sentences/segments. This appears in later syllabus section 8, beyond this guide's main scope.

## What happens if the settings are poor?

- Chunks too large: irrelevant material travels with the answer, context windows fill quickly, and retrieval becomes less precise.
- Chunks too small: context is fragmented, references/definitions can be separated, and more results may be needed to reconstruct a complete idea.
- Overlap too high: repeated text creates duplicate-like results and increases storage/embedding cost.
- Overlap too low: important context at a boundary may be lost.

There is no universal perfect chunk size. Try a small set of chunking configurations and evaluate on actual questions.

## Better default example

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,
    chunk_overlap=120,
    length_function=len,
    # Start with the library's default separator hierarchy.
)
chunks = splitter.split_documents(documents)

assert all(chunk.page_content.strip() for chunk in chunks)
print("documents:", len(documents), "chunks:", len(chunks))
print(chunks[0].metadata)
```

These are starting values, not a benchmark-backed optimum. For code, tables, PDFs, legal material, or token-limited models, tune the strategy to the content.

## Why `split_documents()` is useful

It takes Document objects and generally carries their metadata forward to the resulting chunks. This keeps source information attached to retrieved passages. Always verify this in the output rather than assuming metadata survived every custom transformation.

# 6. Embeddings and vector geometry

## 6.1 Definitions

- **Vector:** An ordered list of numbers representing a point or direction in a mathematical space.
- **Embedding:** A learned numerical representation of an input, often intended to preserve useful semantic or task-specific relationships.
- **Embedding model:** A model that maps inputs such as text (or, for multimodal models, images/audio/video/documents) into vectors.
- **Dimension:** Number of numeric values in each vector. A 384-dimensional embedding contains 384 values.
- **Embedding space:** The vector space in which vectors from a compatible model/configuration can be meaningfully compared.
- **Similarity metric:** A rule for scoring how close or aligned vectors are.
- **Semantic search:** Retrieval based on represented meaning or task-relevant similarity rather than only exact character/keyword overlap.

A vector is not a dictionary definition of a word. Individual dimensions usually do not have human-readable meanings. The model learns a representation that can be useful for comparing items.

## 6.2 Synthetic 2-D vectors vs actual model vectors

Your first notebook plots hand-written coordinates such as `cat = [0.8, 0.6]`. This is valuable for intuition because it can be drawn on a graph. It is not evidence that a real embedding model assigns those coordinates or that actual embeddings have only two dimensions. Your MiniLM example returns 384 values; the OpenAI/Gemini examples return vectors with dimensions determined by the chosen model/configuration.

## 6.3 Why semantically related text can be close

An embedding model is trained to map text into vectors so task-relevant relationships can be compared numerically. A query like “What is LangChain?” may retrieve a passage that describes a framework for applications powered by language models even when the phrasing differs. This is the central benefit over exact keyword matching, but quality depends on the model, text domain, query type, language, chunking, and scoring configuration.

## 6.4 Cosine similarity

For nonzero vectors \(a\) and \(b\):

\[
\operatorname{cos\_sim}(a,b)=\frac{a\cdot b}{\|a\|_2\|b\|_2}
\]

- \(a\cdot b\) is the dot product.
- \(\|a\|_2\) is the Euclidean/L2 norm (vector length).
- Cosine similarity compares angle/alignment, not absolute magnitude.

Typical interpretation for normalized/common embedding workflows:
- Near `+1`: vectors point in similar directions.
- Near `0`: vectors are approximately orthogonal.
- Near `-1`: vectors point in opposite directions.

**Caution:** A score is not automatically a probability or a universal measure of human semantic similarity. The range and calibration depend on the representation and task. Do not compare cosine scores from different embedding models as if they were calibrated on one scale.

Robust implementation:

```python
import numpy as np

def cosine_similarity(a, b) -> float:
    a = np.asarray(a, dtype=np.float64).reshape(-1)
    b = np.asarray(b, dtype=np.float64).reshape(-1)

    if a.shape != b.shape:
        raise ValueError(f"Shape mismatch: {a.shape} != {b.shape}")
    if a.size == 0:
        raise ValueError("Vectors must not be empty")

    norm_a = np.linalg.norm(a)
    norm_b = np.linalg.norm(b)
    if norm_a == 0.0 or norm_b == 0.0:
        raise ValueError("Cosine similarity is undefined for a zero vector")

    return float(np.dot(a, b) / (norm_a * norm_b))
```

## 6.5 Other distance/similarity functions

| Metric | What it measures | Practical note |
|---|---|---|
| Cosine similarity | Angle/directional alignment | Often a sensible baseline for text embeddings. Higher is typically more similar. |
| Dot product / inner product | Sum of pairwise products | Sensitive to vector magnitude unless normalized. Higher may be better for similarity-search indexes. |
| Euclidean/L2 distance | Straight-line distance | Lower is closer; scale and normalization matter. |
| Manhattan/L1 distance | Sum of absolute coordinate differences | Less common for general text retrieval but valid in some systems. |

Do not mix a **distance** with a **similarity** in interview explanations. Distance generally gets better as it decreases; similarity generally gets better as it increases. An integration's `score` name does not by itself tell you which it returns.

## 6.6 `embed_query()` vs `embed_documents()`

- `embed_query(text)` returns one vector for one query.
- `embed_documents(texts)` returns a list of vectors, one for each input document/chunk.

The typical LangChain embedding interface separates these calls because some embedding models support different query/document prompts or task settings. The query and document vectors still need to be compatible: use the same model family/version, dimension, preprocessing assumptions, and task configuration intended for the index.

## 6.7 Why model and dimension consistency matters

A vector index normally expects every stored vector to have one fixed dimension. A query vector must have the same dimension. Even if two vectors have identical dimensions, vectors from unrelated models do not necessarily occupy compatible spaces. Therefore:

1. Record the embedding provider/model and dimension in index metadata/configuration.
2. Do not mix different embedding models in one collection unless the design explicitly supports separate vector fields/spaces.
3. If migrating embedding models, re-embed the corpus and rebuild/reindex it, then evaluate retrieval again.
4. Use a versioned collection/index during migrations so rollback is possible.

These are different components:

- **Embedding model:** converts a query/document into a vector for retrieval.

Your Chroma practical uses Gemini for embeddings and Groq-hosted chat models for generation in parts of the notebook. That is architecturally valid: they have different roles. The important consistency constraint applies between query embeddings and the stored document embeddings, not between the embedding model and the answer-generation model.

## 7.2 Local vs hosted embeddings

**Local model:** data can remain within your environment, no per-request embedding API bill, but you manage downloads, memory, CPU/GPU performance, concurrency, and serving.

**Hosted API:** lower local setup burden and often easier scaling, but requests involve network latency, API limits/cost, external data processing considerations, and provider availability.

Choose using an evaluation dataset, latency/throughput needs, privacy requirements, operational burden, and cost—not only popular model names.

# 8. Build manual semantic search yourself

This exercise makes the retrieval mechanism explicit before a vector database hides the implementation details.

```python
from langchain_huggingface import HuggingFaceEmbeddings
import numpy as np

embeddings = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2",
    encode_kwargs={"normalize_embeddings": True},
)

documents = [
    "LangChain is a framework for LLM applications.",
    "Python is a programming language.",
    "Embeddings map text to numerical vectors.",
    "The weather is sunny today.",
]

# Indexing step: embed each document once.
document_vectors = embeddings.embed_documents(documents)

def cosine_similarity(a, b):
    a = np.asarray(a, dtype=float)
    b = np.asarray(b, dtype=float)
    denom = np.linalg.norm(a) * np.linalg.norm(b)
    if denom == 0:
        raise ValueError("Cosine similarity is undefined for zero vectors")
    return float(np.dot(a, b) / denom)

def semantic_search(query: str, top_k: int = 3):
    if not query.strip():
        raise ValueError("Query must not be blank")
    if top_k < 1:
        raise ValueError("top_k must be >= 1")

    # Query step: embed only the new query.
    query_vector = embeddings.embed_query(query)
    scored = [
        (cosine_similarity(query_vector, vector), text)
        for text, vector in zip(documents, document_vectors)
    ]
    scored.sort(key=lambda item: item[0], reverse=True)
    return scored[:min(top_k, len(scored))]

for score, text in semantic_search("What does LangChain do?", top_k=3):
    print(f"{score:.3f} | {text}")
```

## Complexity intuition

- Embedding the corpus costs time/API calls during indexing.
- A naive exact scan over `N` vectors of dimension `d` compares the query against all vectors, roughly proportional to `N × d` work per query.
- A vector index/database can reduce query work, support efficient filtering, and handle persistent/managed operations. Some indexes use approximate nearest neighbours, trading a controllable amount of recall/accuracy for speed and memory.

For the toy list above, a full vector database may be unnecessary. A database becomes useful when you need durable storage, larger corpora, updates, access control, operational reliability, or multi-user query traffic.

# 9. Vector store vs vector database

## Definitions

- **Vector store (broad usage):** A component/library/interface that stores or indexes vectors and retrieves similar items.
- **Vector database:** A database system designed to manage vector data and similarity retrieval, often alongside metadata filters, CRUD operations, persistence, APIs, scaling, access controls, and operational features.
- **Vector-search library:** A lower-level library for efficient nearest-neighbour search, which may not provide a database server, multi-tenancy, authentication, backups, or managed operations.

Terminology is not fully standardized. Some products are referred to as both vector stores and vector databases depending on whether the author is describing an integration, a local mode, or the full system. Interviewers usually care more about the responsibilities and trade-offs than an absolute naming rule.

## Decision table

| Need | Reasonable starting point | Why |
|---|---|---|
| Learning, quick prototype, tiny dataset | In-memory vector store | Minimal setup; data can disappear when the process ends. |
| Local app/research with persistent data | Chroma local persistence | Easy to iterate on local collections; verify backup and concurrency needs before production. |
| Custom local nearest-neighbour index | FAISS | High-performance similarity-search library; application owns surrounding storage/API/operations. |
| Managed production vector retrieval | Pinecone or another managed vector DB | Less infrastructure to operate yourself; consider cost, region, access control, filtering, backups, latency, and lock-in. |
| Existing Cassandra ecosystem / managed database needs | DataStax Astra DB vector search | May fit an organization already invested in that platform and its operational model. |
| Self-managed large-scale vector service | Evaluate Qdrant, Milvus, Weaviate, Vespa, and others | Compare required filtering, ingestion throughput, hybrid search, replicas, deployment skills, and operations. |

The image in the uploaded comparison PDF uses “under one million vs billions” as a rough illustration. **Do not treat one million as a technical cutoff.** Corpus size alone does not determine the right product. Query rate, vector dimension, latency target, filtering, durability, deployment, access model, updates, and operating budget also matter.

## Database capabilities to understand

- **CRUD:** Create, read, update, delete records.
- **Collection/index:** Logical grouping of vectors/documents and their configuration.
- **IDs:** Stable identifiers for insert/update/delete and source traceability.
- **Metadata filtering:** Restricts candidates by structured conditions such as topic, tenant, date, or access group.
- **Persistence:** Data survives application restarts.
- **Index:** Data structure used to speed up retrieval.
- **ANN (Approximate Nearest Neighbour):** Finds close vectors efficiently without necessarily calculating the exact nearest neighbours over the entire corpus.
- **Sharding:** Divides data across partitions/nodes.
- **Replication:** Keeps copies for availability/recovery/scaling.
- **High availability:** Designed to keep serving despite certain failures.
- **Multi-tenancy:** Separates the data/access of different users or organizations.
- **Filtering:** Narrows eligible records before or during retrieval.

# 10. ChromaDB — concepts and code

## What it is

Chroma is an open-source vector database that can be used locally and through server/cloud deployment options. It manages a collection of text/data, embeddings, IDs, and metadata and exposes retrieval operations. Its current LangChain integration is documented in the `langchain-chroma` package.

## Key operations

- `Chroma(...)`: Connect to or create a collection.
- `Chroma.from_documents(...)`: Embed and index LangChain Documents through the embedding integration.
- `add_documents(...)`: Add more Documents, often with explicit IDs.
- `similarity_search(query, k=...)`: Return the most relevant matching Documents.
- `similarity_search_with_score(...)`: Return Documents with raw store-specific distance/score values; inspect metric semantics.
- `as_retriever(...)`: Adapt the vector store to LangChain's retriever interface.
- `persist_directory=...`: Configure local persistence in the integration where supported.

## Canonical local Chroma example

```python
from langchain_core.documents import Document
from langchain_chroma import Chroma
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2"
)

documents = [
    Document(
        page_content="Machine learning learns patterns from data.",
        metadata={"source": "ml_notes.txt", "topic": "ML"},
    ),
    Document(
        page_content="Deep learning uses multi-layer neural networks.",
        metadata={"source": "dl_notes.txt", "topic": "DL"},
    ),
]

vector_store = Chroma.from_documents(
    documents=documents,
    embedding=embeddings,
    collection_name="revision_demo",
    persist_directory="./chroma_revision_db",
)

# Retrieve without generating an LLM answer.
results = vector_store.similarity_search(
    "What are neural networks?",
    k=2,
)
for result in results:
    print(result.page_content, result.metadata)

# Add a new chunk later. Supply a stable ID in production.
vector_store.add_documents(
    [Document(
        page_content="Supervised learning uses labelled examples.",
        metadata={"source": "ml_notes.txt", "topic": "ML"},
    )],
    ids=["ml-supervised-001"],
)

# Metadata-filtered query; filter syntax depends on integration/version.
ml_results = vector_store.similarity_search(
    "learning from examples",
    k=3,
    filter={"topic": "ML"},
)
```

Install for the above current integration style:

```cmd
uv add langchain-chroma chromadb langchain-core langchain-huggingface sentence-transformers
```

**Notebook compatibility note:** your notebook imports `Chroma` from `langchain_community.vectorstores`. Current LangChain integration documentation uses `from langchain_chroma import Chroma` and the separate `langchain-chroma` package. Choose one dependency/API set and pin compatible versions rather than randomly mixing versions.

## Important Chroma gotchas

1. A persistent directory is not the same as a backed-up, highly available production database.
2. `similarity_search_with_score()` may return a distance (for example, a smaller distance is better), not a calibrated probability. Verify the installed integration's exact semantics.
3. Metadata types and filter syntax have constraints. Store simple, queryable metadata types; test filters.
4. Provide stable IDs for incremental updates and deletions. Avoid duplicate inserts when rerunning ingestion.
5. Reuse the same embedding model/configuration for query and indexed documents.
6. If you directly access private `_collection` APIs to insert existing vectors, you become responsible for keeping IDs, vectors, documents, metadata, and dimensions aligned. Prefer the public API where possible.

# 11. FAISS — concepts and code

## What it is

**FAISS** (Facebook AI Similarity Search) is a library for efficient similarity search and clustering over dense vectors. It is useful when you want local, customisable vector indexing. It is not by itself a complete managed, multi-tenant database service.

## Your notebook's FAISS flow

```text
LangChain Documents → RecursiveCharacterTextSplitter
→ OpenAIEmbeddings → FAISS.from_documents
→ similarity_search / metadata filter
→ optional save_local / load_local
→ retriever → LCEL prompt → chat model
```

## Minimal implementation aligned with the notebook

```python
from langchain_core.documents import Document
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter

source_docs = [
    Document(
        page_content="Machine learning finds patterns in data.",
        metadata={"source": "ml.txt", "topic": "ML"},
    ),
    Document(
        page_content="Deep learning uses multi-layer neural networks.",
        metadata={"source": "dl.txt", "topic": "DL"},
    ),
]

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    # Use default separator hierarchy initially.
)
chunks = splitter.split_documents(source_docs)

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
faiss_store = FAISS.from_documents(chunks, embeddings)

hits = faiss_store.similarity_search("What is deep learning?", k=2)
for doc in hits:
    print(doc.page_content, doc.metadata)

# Save and reload only from a trusted local index.
faiss_store.save_local("faiss_revision_index")
reloaded = FAISS.load_local(
    "faiss_revision_index",
    embeddings,
    allow_dangerous_deserialization=True,
)
```

The `langchain-community` FAISS integration imports a local FAISS library, so installation can vary by operating system/Python version. Keep the environment reproducible and test install commands on the target machine.

## Why local persistence is useful

It avoids recomputing the index on every restart for the same corpus and permits a repeatable local experiment. But an index artifact needs versioning and lifecycle management. When source data changes, you need a deliberate update/delete/rebuild strategy.

## Security note: dangerous deserialization

A serialized index may involve a pickle file. Pickle deserialization can execute code when loading a malicious or tampered artifact. The `allow_dangerous_deserialization=True` flag is an explicit trust decision, not a fix for the risk. Load only artifacts from a trusted source, protect file permissions, and verify integrity.

## FAISS score interview note

A method name containing “similarity” does not guarantee a cosine similarity score. The underlying FAISS index may use L2 distance or inner product depending on configuration. Ask: What metric is configured? Is the score a distance or similarity? Is the vector normalized? Does higher or lower mean better? Only then interpret it.

# 12. In-memory, Pinecone, and DataStax Astra DB

## In-memory vector store

**Definition:** A vector store that keeps indexed vectors in process memory instead of durable database storage.

**Use for:** tests, tutorials, prototypes, small ephemeral workflows, or when rebuilding the index at startup is acceptable.

**Avoid as the only production persistence layer when:** restarts must not lose data, multiple workers must share an index, or operational durability is required.

The course includes an in-memory vector store lecture. In modern LangChain, `InMemoryVectorStore` is also available through `langchain_core.vectorstores` for simple testing examples.

## Pinecone

**Definition:** A managed vector database service for storing/indexing embeddings and retrieving vectors with metadata filtering and operational features.

**Use when:** you want a hosted vector service and do not want to operate the full vector infrastructure yourself.

**Evaluate:** latency/region, namespace or tenant design, filtering requirements, upsert/delete behavior, pricing, index configuration, backup/export, security, and provider lock-in. Read current provider docs for exact SDK syntax before coding because hosted SDKs evolve.

## DataStax Astra DB

**Definition:** A managed database service built around the Cassandra ecosystem that supports vector search as well as other database functionality.

**Use when:** its operational model, existing Cassandra ecosystem, managed platform, and query features fit the application. Consider the actual vector features and service tier available to you rather than choosing it just because it is called a vector DB.

## How to compare vendors in an interview

Don't merely list brand names. Compare:
1. Deployment: embedded/local, self-hosted server, or managed cloud.
2. Scale and query/ingestion throughput.
3. Search methods and supported distance metrics.
4. Metadata filtering and hybrid retrieval.
5. Updates, deletes, persistence, backup/restore.
6. Availability, replicas, partitions, and multi-tenancy.
7. Access control, data residency, monitoring, and cost.
8. Ease of migration and vendor lock-in.

# 13. Retrievers, top-k, and metadata filters

## Definition: retriever

A **retriever** is an abstraction that accepts a query and returns relevant Documents. It can be backed by a vector store, a keyword search engine, a database query, or a more advanced retrieval strategy.

In LangChain, `vector_store.as_retriever()` gives a retriever interface to a vector store.

## Top-k

`k` is the maximum number of documents/chunks requested. For example, `k=3` asks the retriever for up to three results. It is not a quality score and does not guarantee all three are relevant.

- Too low: relevant evidence may be omitted.
- Too high: irrelevant context, latency, and prompt-token usage can grow.
- Tune `k` using test questions and retrieval metrics rather than guessing.

## Metadata filtering

A vector query with a filter first restricts what is eligible (or applies filtering during retrieval depending on the engine), then selects relevant candidates. Example: only search the HR policy collection for a user authorized for HR policies. Filtering can be a correctness and security boundary, but the application must enforce access control reliably; don't rely on prompt instructions alone.

## Similarity threshold

A threshold requires results to pass a score/distance cutoff. Since score semantics vary, verify whether the configured integration expects a minimum similarity or maximum distance. A threshold that is arbitrary or copied from another model may reject good results or accept bad ones.

# 14. Basic RAG with LCEL: explain every component

Your FAISS and Chroma notebooks use the same general flow: retriever → format documents → prompt → LLM → output parser.

## LCEL definition

**LangChain Expression Language (LCEL)** is LangChain's compositional interface for connecting runnable components using pipelines and mapping/parallel composition. The `|` operator pipes one runnable's output into the next.

- `RunnableParallel`: computes multiple named inputs from the same input.
- `RunnablePassthrough`: passes the input through unchanged.
- `ChatPromptTemplate`: formats messages with variables.
- `StrOutputParser`: converts a model output to plain text.
- `retriever.invoke(question)`: returns a list of Documents.
- `format_docs(docs)`: joins retrieved `page_content` into the context string.

## Compact LCEL pattern

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableParallel, RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template(
    """Answer only from the supplied context. If the answer is absent, say you do not know.

Context:
{context}

Question:
{question}

Answer:"""
)

def format_docs(docs):
    return "\n\n".join(
        f"Source: {doc.metadata.get('source', 'unknown')}\n{doc.page_content}"
        for doc in docs
    )

rag_chain = (
    RunnableParallel({
        "context": retriever | format_docs,
        "question": RunnablePassthrough(),
    })
    | prompt
    | llm
    | StrOutputParser()
)

answer = rag_chain.invoke("What is deep learning?")
print(answer)
```

This code assumes `retriever` and `llm` are already initialized. It follows the LCEL pattern demonstrated in the notebook; exact package imports/model setup should match the project's pinned LangChain versions.

## Why separate retrieval and generation?

The vector store does not write the final answer. It returns Documents. The prompt decides how those Documents are presented, and the chat model generates a response. Keeping the stages separate makes it easier to debug a bad answer:

- Wrong evidence returned → investigate parsing, chunking, embedding compatibility, index settings, filters, query wording, or `k`.
- Good evidence but unsupported answer → investigate prompt, model behavior, context ordering, token limit, or answer validation.
- Correct content but no provenance → pass and render stable source metadata explicitly.

## Traditional RAG doesn't require agents

A basic RAG chain is generally a predictable sequence of retrieval and generation. Agentic RAG is a later course topic and may decide when/how to retrieve, use tools, revise queries, or repeat retrieval. Don't use an agent when a simple chain reliably solves the task; every extra decision can add latency, cost, and failure modes.

# 15. Basic conversational RAG and memory

## Definitions

- **Chat history:** Previous user and assistant messages included in the next turn.
- **Conversational RAG:** A RAG pipeline that uses the current query plus conversational context to understand follow-up questions.
- **Short-term conversational state:** Messages needed within the current dialogue/session.
- **Persistent memory:** State saved across sessions or requests; a separate design problem that needs storage, retrieval, update, and privacy policies.

A user may ask “What is machine learning?” and then “How is it different from traditional programming?” The second question is underspecified on its own. A query-rewriting step can convert the follow-up into a standalone query such as “How is machine learning different from traditional programming?” before retrieval.

## What was wrong with the notebook example?

The FAISS notebook makes `chat_history = []`, invokes the chain once, then invokes a follow-up with the same list. It does not append `HumanMessage`/`AIMessage` objects or otherwise update that state. The chain has a placeholder for history, but the example does not actually maintain history between turns.

Conceptually, the update loop is:

```python
from langchain_core.messages import HumanMessage, AIMessage

chat_history = []

# after generating a1 for q1:
chat_history.extend([
    HumanMessage(content=q1),
    AIMessage(content=a1),
])

# On the next turn, pass the updated history to the chain.
```

The exact chain input depends on the specific prompt and chain. For long conversations, don't send unlimited history forever. Use a history window, summarization, or a dedicated memory strategy when justified. Also distinguish conversation history from enterprise knowledge: history tracks the dialogue; vector retrieval searches the knowledge base.

# 16. Interview glossary: concise definitions to memorize

1. **RAG:** Retrieve external information and give it to an LLM as context for a grounded response.
2. **Ingestion:** Bringing source data into the indexing pipeline.
3. **Parsing:** Extracting usable text/structure from a source format.
4. **Preprocessing:** Cleaning and normalizing parsed data before indexing.
5. **Chunking:** Splitting content into smaller units for embedding and retrieval.
6. **Chunk overlap:** Repeating part of adjacent chunks to preserve boundary context.
7. **Metadata:** Structured attributes used for provenance, filtering, authorization, and display.
8. **Embedding:** A learned numeric vector representation of an input.
9. **Embedding model:** A model that maps supported content to vectors.
10. **Vector dimension:** Number of coordinates in a vector.
11. **Embedding space:** A vector space in which outputs of a compatible embedding configuration are comparable.
12. **Cosine similarity:** Dot product divided by the product of vector norms; measures directional alignment.
13. **Semantic search:** Retrieval based on embedding-space similarity rather than only exact lexical overlap.
14. **Vector index:** A data structure optimized to retrieve nearby vectors efficiently.
15. **Vector store:** A component that stores/indexes vectors and exposes retrieval operations.
16. **Vector database:** A database system for vector retrieval plus data-management capabilities such as persistence, CRUD, metadata filtering, and often scalable service operations.
17. **FAISS:** A similarity-search and clustering library for dense vectors.
18. **Chroma:** An open-source vector database with local and server/cloud usage options.
19. **Pinecone:** A managed vector database service.
20. **DataStax Astra DB:** A managed database platform built around Cassandra that supports vector search.
21. **Collection:** A logical group of vectors/documents and their index settings in a vector system.
22. **Top-k:** The maximum number of nearest/relevant candidates requested from search.
23. **Retriever:** An interface that returns relevant Documents for a query.
24. **Metadata filter:** A structured constraint restricting eligible documents during retrieval.
25. **Persistence:** Retaining indexed data beyond a process/session restart.
26. **CRUD:** Create, read, update, and delete operations on records.
27. **ANN:** Approximate nearest-neighbour search, which trades exactness for speed/resource efficiency.
28. **LCEL:** LangChain's compositional expression interface for chaining runnables.
29. **Grounded answer:** An answer whose claims are supported by the supplied/retrieved evidence.
30. **Embedding migration:** Re-embedding/reindexing corpus data when the embedding model or incompatible configuration changes.
31. **Recall@k:** Fraction of relevant items found within the top-k retrieved results.
32. **Precision@k:** Fraction of the top-k returned results that are relevant.
33. **Latency:** Time taken to perform an operation or complete a request.
34. **Reranking:** Reordering a retrieved candidate set using a more targeted relevance scoring model or strategy; covered later in the course syllabus.
35. **Hybrid search:** Combining lexical/sparse and vector/dense retrieval; covered later in the course syllabus.

# 17. Interview questions and model answers

## Q1. Explain RAG end to end.

“I first ingest and parse the data, clean it, split it into retrievable chunks, preserve source metadata, generate an embedding per chunk, and index the vectors. At query time I embed the user question, retrieve the top-k relevant chunks, optionally apply metadata filters, build a prompt using that evidence, and call the LLM. I inspect both the retrieved chunks and the answer because a good generation step cannot reliably compensate for missing or incorrect retrieval.”

## Q2. Why do we need embeddings?

“Embeddings map text into numeric vectors that can be compared using a similarity or distance function. They let us retrieve passages that are semantically related even when query wording differs from the source wording. They are not guarantees of relevance, so we still evaluate retrieval on realistic queries.”

## Q3. Why not use keyword search alone?

“Keyword search is strong for exact terms, IDs, product names, and precise phrases. Embedding search can capture paraphrases and semantic relationships. Which one is better depends on the query. A later-stage RAG design may use both, but I would first measure the failure modes rather than assume dense retrieval always wins.”

## Q4. What is cosine similarity?

“It is the dot product of two vectors divided by the product of their L2 norms. It measures directional alignment and is often used to compare embeddings. I check zero vectors and matching dimensions, and I do not interpret its score as a probability.”

## Q5. What is the difference between `embed_query` and `embed_documents`?

“`embed_query` returns one vector for a single query; `embed_documents` returns one vector per text in a batch. In our pipeline, document vectors are computed during indexing and reused, while the current query is embedded at query time. Query/document task settings must still be compatible.”

## Q6. Why cache document embeddings?

“Re-embedding the whole corpus on every query repeats expensive computation and increases latency/cost. We build the index once and re-embed only new or changed documents. We also track the model and content version so we know when a cached vector is invalid.”

## Q7. Why chunk instead of embedding a whole PDF?

“Large documents contain multiple topics. A single vector may be too broad, and the content may exceed model or prompt limits. Chunking improves passage-level retrieval and lets us preserve page/source metadata. Chunk size and overlap are empirical choices that I evaluate.”

## Q8. Chroma vs FAISS?

“FAISS is a similarity-search library that gives strong control over local vector indexing; I have to handle the surrounding storage, persistence, and application/service responsibilities. Chroma provides a higher-level vector database interface with documents, metadata, collections, local persistence, and retrieval methods. I choose based on deployment, filtering, durability, scale, and operational requirements.”

## Q9. What is the difference between a vector store and a vector database?

“I use ‘vector store’ broadly for the component that holds/indexes vectors and retrieves neighbours. ‘Vector database’ usually emphasizes database capabilities such as persistent data management, metadata filters, CRUD, APIs, availability, and scaling. The terminology overlaps, so I compare actual capabilities rather than relying on the label.”

## Q10. Does a vector database generate the final response?

“No. It retrieves the closest or most relevant candidate records. The application passes the retrieved content into a prompt and the LLM generates an answer. Retrieval and generation are separate stages and need separate debugging/evaluation.”

## Q11. What does top-k mean?

“It controls how many candidates are returned. A small k may miss evidence; a large k can add irrelevant context and cost. I tune it on a test set and, where useful, use score thresholds or reranking.”

## Q12. What are metadata and metadata filters used for?

“Metadata records attributes such as source, page, date, tenant, or topic. A filter restricts eligible candidates—for example, returning only documents the user is allowed to access. Metadata also supports citations and source traceability.”

## Q13. Why must query and document vectors use the same embedding model?

“They need to live in a compatible vector space with the same dimensions and task settings. A query vector from one unrelated model generally cannot be compared meaningfully with stored vectors from another. Changing models usually requires re-embedding and reindexing the corpus.”

## Q14. What is persistent storage?

“It means the collection/index survives a program restart. It does not automatically mean the system has backups, replication, high availability, or production-grade disaster recovery; those are separate operational capabilities.”

## Q15. How do you debug a wrong RAG answer?

“I inspect the pipeline in order: parsed text, chunk boundaries, metadata, query embedding and dimension, retrieved top-k passages, the actual prompt/context, and then the model response. If retrieval is bad, I fix indexing or retrieval. If retrieval is good but the answer is unsupported, I improve grounding instructions, context formatting, or output validation. Then I evaluate on a repeatable query set.”
